# Code Style and Formatting Rules

This is the single code-style guide for the fleet. The **General** section applies to every language. Each **language section** (.NET, Python, Shell, PowerShell) is self-contained: a repo follows only the section(s) for the languages it ships and ignores the rest. A repo keeps the whole file rather than trimming it. An unused-language section costs nothing, the same whole-file model as [`.editorconfig`][root], whose inert `[*.cs]` block a non-.NET repo keeps.

Cross-cutting *process* rules live in [GOVERNANCE.md][governance] and are not repeated here. They cover PR titles, branching, US English, Markdown style, comments philosophy, workflow YAML, and PR review etiquette. They also cover the verification discipline that defines the pre-push lint gate.

## General

These rules apply to every language in the repo.

### Tooling Names and Casing

Use each tool's official casing in task labels, docs, and prose, per the `comment-and-doc-style` Skill at `.agents/skills/comment-and-doc-style/SKILL.md` in the hub. That is not a repo-relative link, since the path is hub-local and not carried into every fleet repo.

### Toolchain Versions

Where the hub carries a baseline file that selects a language's toolchain line, that file sets the fleet's default line once. Each repository selects its own line in its own copy of that file. That copy is the repository's source of truth, and the hub's workflows install the line it selects. They fall back to the hub's default only where a repository carries no selector.

- **A repository may lead or lag the default.** One repository can move to a newer major while the fleet stays, or hold an older line while the fleet moves.
- **A move edits the selector and every setting that names the same line, together.** These include a target framework, a devcontainer image tag, and any fixed language version.
- **The language level follows the selected line.** It is left unset wherever the toolchain derives it from the line, and set by hand only where it does not.
- **A resync never changes the line a repository selects.** It carries the baseline file's fleet-owned settings and leaves the repository's own choice of line in place.
- **The audit checks that a repository agrees with itself.** Its settings must name one line between them, and that line need not be the hub's default.

### Clean-Compile Verification

Each language defines a **clean-compile** verification: the combination of build, formatter, linter, and code-analysis tools that must report clean before a commit. It is exposed as one or more **named** VS Code tasks (or, where a language ships no tasks, documented commands). Those definitions are the same across the fleet. Each language's definition is in its section below or in the Skill that section names.

- **Run it after every code change, and it is not the whole gate.** The relevant language's clean-compile must pass before you commit. CI runs those same language checks as a backstop **plus everything else its validation workflow runs**. All of it reports into the one required status. A green clean-compile therefore does not predict a green CI. That remainder is at least the doc-lint set (markdownlint, cspell, actionlint, `editorconfig-checker`) and whatever spec, config, and script gates the repo carries. So read the workflow for the full list rather than assuming the previous sentence enumerates it. What has to pass before a push is the repo's **whole** lint gate, per [GOVERNANCE.md "Verification Discipline"][governance-verification-discipline]. Each linter's known-working invocation is in `GOVERNANCE.md` "Running the Linters Locally (Known-Working Invocations)", a hub-only section read in a hub checkout rather than carried into every fleet repo.
- **The named task definition is the canonical spec** - its exact command sequence, arguments, and strictness. You may run it through the VS Code task **or** by invoking the equivalent native commands directly. Either is fine **only if the sequence, arguments, and strictness match exactly**. No shortcuts and no more-lenient options (for example, never drop `--verify-no-changes` or loosen a `--severity`).
- **A working local commit/pre-commit gate is strongly suggested fleet-wide, and its absence is a measured audit finding.** The *mechanism* is bounded by the toolchain the repo already keeps rather than by which languages its checks cover, and canonical shapes carry it. Husky.Net runs from a .NET tool manifest declaring it, so a repo that keeps no such manifest uses the `pre-commit` framework instead. Any repo may also wire an equivalent hook of its own at `.husky/pre-commit`, enabled with `core.hooksPath` and sourcing nothing. Canonical shapes for Husky.Net and the `pre-commit` framework live in `catalog/snippets/` in the hub. That is not a repo-relative path, since it is hub-local and not carried into every fleet repo. What that gate must cover and its per-clone enablement steps are not restated here. They are in `GOVERNANCE.md` "Running the Linters Locally (Known-Working Invocations)", the same hub-only section.

### Analyzer Diagnostics and Suppressions

- **A new port is not a license to silence diagnostics.** Brownfield / just-ported status never justifies relaxing analyzer or linter severities or muting newly surfaced warnings. Fix them.
- **Suppress only genuine false-positives or deliberate, documented exceptions**, always at the **narrowest scope that fits**, in this order of preference:
  1. An **in-code annotation on the specific symbol**, with a justification, in the language's attribute/comment form, never a blanket pragma spanning a region.
  2. The **owning project's local config** when the exception is project-wide for one project (e.g. a test project's own `.editorconfig` / `pyproject.toml`).
  3. The **root / shared config** only when the suppression is genuinely applicable to **every** project in the repo.
- **Never blanket-relax a batch of rules project-wide** to get a port to build. The per-language mechanics (which attribute, which config key) are in the Skill a language section names, where it names one.

### Operations and Failure Messages

- **Let the real operation be the check, not a prediction of it.** Attempt the read, the write, or the call itself, and turn its failure into a clean refusal. Do not probe first with an existence, type, or permission test. Where the operation could block or succeed on the wrong kind of target, judge what it opened instead. A probe is a second model of the operation. It misjudges each case its author did not foresee, such as a dangling link, a link loop, or a platform's own permission model. The operation cannot disagree with itself.
- **Classify a subprocess failure by which command failed and the status code it reports, never by the prose of its message.** That prose varies by tool version and locale, and a status code's value does not, even one printed inside the message. A printed code is read by the notation that marks it, and a match finding none counts as an unexpected failure. Where one command's status code cannot separate the failures its caller handles differently, give each expected failure its own real operation. Where no such operation exists, treat the failure as unexpected. A test asserting a script's output, such as the refusal "Command-Line Arguments" requires, verifies that output rather than classifying a failure.
- **A failure message states the error, the path or other target, and the remedy, and claims nothing about the state the failure left.** The error the operation raised is the one fact the code holds at that point. A description of what the failure left behind is a prediction. It reads false once an unforeseen state reaches the message, such as a file written in full that then fails to close. A remedy such as "fix what it names, then re-run" needs no such claim.

### Interrupts

This applies to every shell and Python script. `CODESTYLE.md` "Interrupts in Python" and "Interrupts in Shell" state each language's mechanics.

- **On SIGINT or SIGTERM, a script releases what it holds before it exits.** It removes the temporary paths it created, releases the locks it took, and stops the child processes it started. A path, lock, or child left behind can stop the next run from starting, or feed it a half-written input. A script started with SIGINT ignored keeps it ignored, so a stop meant to reach it sends SIGTERM. A non-interactive shell starts a background child that way.
- **A write to persistent state goes to a temporary path beside the target, then is renamed over it.** An interrupt then leaves the old content or the new, never a mix of both. A store with transactions of its own, such as an SQLite database, is written through those instead. A rename over an open database can corrupt it.
- **An interrupted script prints one line naming the signal, with no traceback, and ends by re-raising the signal.** The signal then ends the process, so a shell reports 130 for SIGINT or 143 for SIGTERM, 128 plus the signal number. At Ctrl-C, a calling shell's loop then stops rather than starting its next iteration. A script calling `exit 130` has not died by the signal, so that loop reads an ordinary non-zero exit and runs on. A launcher between them, such as `uv run`, exits with the status rather than dying by the signal, so that loop runs on there too.
- **A script takes this rule when it is created or next edited.** An existing script is not edited for this rule alone.
- **A script that holds a lock, temporary state, or a child process owes a test that signals it mid-run.** The test sends SIGINT or SIGTERM, then asserts that the script died by that signal and that nothing it held remains. It starts the script with its interpreter directly, since a launcher such as `uv run` hides the signal death. It is skipped on Windows, which cannot deliver either signal for a script to handle. A script holding none of these owes no such test.
- **A script that ends by `exec`-ing its long-running process owes no interrupt handling for that process.** The `exec` replaces the script, so a signal reaches the process directly. A background child the script starts to outlive the `exec` is handed across it, and the script neither stops it nor waits for it. Such a child is handed across only where something else stops it, such as a container's teardown of its whole process tree. Anything else the script holds is released before the `exec`. A script that holds nothing else at any point before the `exec` owes no trap and no signal test. As PID 1, such as a container's entrypoint, it ignores a SIGTERM that arrives before the `exec`, so a stop waits for its timeout.

### Parsing Structured Formats

- **A program reading a structured format uses a maintained parser rather than a hand-written one, where a field-tested parser exists for the runtime in use.** That covers YAML, Markdown, TOML, JSON, a programming language's comments or strings, and a shell command line. The standard library's own parsers count, such as Python's `json`, `tomllib`, `ast`, `tokenize`, and `html.parser`. A hand-written reader converges on the format's full grammar one review finding at a time, and every script that grows one pays that cost again.

### Command-Line Arguments

A command-line script is one a person or an agent runs by name. A hook its host runs, taking its input from that host rather than from a command line, is not one.

- **Every command-line script answers `--help` and `-h`** with the same text on stdout, then exits 0, changing nothing. That text opens on a usage line naming the script. An agent learns a script's interface by asking it, so a script that reads `--help` as an input acts in a way nobody predicted. A PowerShell script declaring its own parameters answers `-Help` and `-h` instead, from a `-Help` switch carrying an `h` alias. That form follows PowerShell's own parameter convention, so such a script owes no answer to a literal `--help`. A wrapper that forwards its arguments to another script answers whatever that script answers.
- **An argument the script does not recognize is refused**, with a non-zero exit before any read or write. The refusal names it as an unknown or unrecognized option, argument, flag, or parameter, and PowerShell's own refusal of a parameter it cannot bind counts. That refusal comes from the binder only in an advanced script, one carrying `[CmdletBinding()]` or a `[Parameter()]` attribute. Without either, a plain `param()` block binds an unknown parameter into `$args` and runs on. Such a script refuses a non-empty `$args` itself, before any work. So a PowerShell script declaring its own parameters refuses a literal `--help` like any other unrecognized argument. A script with a parameter taking the remaining arguments refuses a dash-prefixed leftover itself. An unrecognized first argument is never taken as a default mode or as a target.
- **A shell script that gives a refused argument an exit status of its own uses 64, `EX_USAGE` from `sysexits.h`, and reserves it.** A caller can then tell a refusal, which changed nothing, from a run that started and failed, without reading the message. Every refusal exits through one function that exits 64. Under `set -e` a failed command's own status becomes the script's, so an `EXIT` trap turns any other exit carrying 64 into 1. A program the script `exec`s replaces that trap. So the script `exec`s only a program whose own 64, if it exits 64 at all, means a refused argument. An argument the script passes on, which that program refuses, keeps the program's status. The script's `--help` names the status, so a caller reads it as a contract.

### Script and Utility File Names

| Type | Rule | Basis |
| --- | --- | --- |
| Python `.py` | lowercase snake_case | [PEP 8][pep8-names-link] module naming. A hyphenated module also cannot be named in an `import` statement |
| Shell `.sh` and PowerShell `.ps1` | lowercase-hyphenated | The Linux command convention. A cross-platform pair keeps one name, `sync-tools.sh` beside `sync-tools.ps1` |
| Windows batch `.cmd` and `.bat` | lowercase-hyphenated | The same convention as shell and PowerShell. A shim that puts a command on `PATH` takes the name of the command it provides, `sync-tools.cmd` launching `sync-tools.ps1` |
| PowerShell functions inside a `.ps1` | Verb-Noun with an approved verb (`Get-Verb`) | PSScriptAnalyzer `PSUseApprovedVerbs`. This is a command rule, not a file rule |
| Env and secret files, tracked or not | lowercase fields joined by `_`, with no dot but the extension | `mail_relay.env`, `db_root_password`, `app_web-01_prod.env` |
| Env variable names and CI secret names | UPPER_SNAKE_CASE | The POSIX and GitHub convention |

- **Installed commands.** An executable or launcher on `PATH` or in a system slot (systemd, cron, run-parts, motd) is named as a command, whatever its language. That name is lowercase-hyphenated. It carries no extension unless the platform needs one to run it, such as `.cmd` or `.ps1` on Windows.
- **Wrapper exemption.** A thin launcher whose only job is to run a Python tool keeps that tool's stem, so `fetch_report.py`, `fetch_report.sh`, and `fetch_report.ps1` stay grouped together. It covers only a launcher run by its path. A launcher installed onto `PATH` or into a system slot is an installed command instead, such as `fetch-report` rather than `fetch_report`.
- **Env and secret file names reach every file a repository names.** That covers a tracked file or template and a secret file mounted into a container. It also covers a host-side file the repository's docs or scripts name, such as an `ENV_FILE` path or a compose `env_file`.
- **`_` joins the fields of an env or secret file name, and each field keeps its own valid form.** A host name field stays verbatim, hyphens included, so `app_web-01_prod.env` is right and `app_web_01_prod.env` and `app.web-01.prod.env` are not. That field is a short name, the host's first DNS label (`web-01`) or a logical role name (`vps-staging`), and never a fully qualified one. Either way it takes the DNS label form, so its own words join with `-`. A repository name field takes the repository's name in lower case, hyphens kept, as in `github_example-repo_codecov_token`. GitHub allows `_` and `.` in a repository name too. A repository whose name carries either cannot form this field, so it may name no env or secret file that needs one. In every other field a hyphen never joins words, since that is the job of `_`. A host name label can carry `-` and never `_`, so every `_` is a separator and the name splits back into its fields. The name is lowercase, carries no dot but its extension, and starts and ends with a letter or digit. A tracked template's `.example` suffix is not counted as a dot.
- **A variable name converts separately.** An env variable or CI secret name allows only `A-Z`, `0-9`, and `_`. Where a field becomes one, the hyphen becomes `_` there, as in `APP_WEB_01_PROD_TOKEN`, and never in the file name.
- **Some consumers set limits of their own.** A name used as a Docker secret stays within the 64 characters Docker allows. A name that maps to an env variable or CI secret does not start with a digit, which POSIX and GitHub both forbid.
- **Externally fixed names are exempt.** That covers Git hook names, `__init__.py`, `conftest.py`, and Pester's `.Tests.ps1` suffix, whose stem mirrors the script under test. It covers a PowerShell data file (`.psd1`) whose name a tool fixes, such as a module manifest named for its module. `PSScriptAnalyzerSettings.psd1` is another, since PSScriptAnalyzer finds it by that name. So is an env file a tool reads by a fixed name, such as `.env`, `.env.local`, or `.env.production`. An env or secret file in a `.secrets/` directory is never one, since it is read by a path the repository configures. The exemption also covers any name a platform defines.
- **Directories are out of scope.** That means directory names. How a repository splits its Python across directories is a profile rule, stated in the "Python" section below.

Departures, stated on purpose so a reader does not "fix" them back:

- The [Google Shell Style Guide][google-shell-link] asks for underscores in shell file names. The fleet uses hyphens instead, matching installed Linux commands.
- Microsoft's [approved verbs][ps-approved-verbs-link] govern command names. A `.ps1` run by path is a file rather than an exported command, so the file takes the shell convention and its functions take Verb-Noun.

### Markdown and Spelling

These rules apply repo-wide, in every directory. Markdown lints clean via `markdownlint-cli2` against the shared config. Spelling is US English via CSpell against the shared `cspell.json`, and the CI spelling gate covers `README.md` and `HISTORY.md` only. `HISTORY.md` mirrors the README's opening, and "Markdown" is a proper noun in prose. A repo excluding a subtree of its own that it does not treat as authored prose puts a `.markdownlint-cli2.jsonc` beside that content. That file carries its own `ignores`, instead of the repo editing the shared root config, whose contents are fleet-fixed. A committed data archive, a vendored theme, and a hand-maintained record each count as such a subtree. Those `ignores` patterns resolve against the directory holding them rather than against the repo root. So a repo-root-relative entry there matches nothing and reports no error saying so. Excluding through the CI workflow's own negated Markdown glob input instead is a CI-only fix. It leaves the same files flagged for anyone running the linter locally. The full rules are in the `comment-and-doc-style` Skill referenced above.

### PlexCleaner .NET Conventions

The conventions below are this repo's own, beyond the carried rules.

- **The clean-compile is the `.NET Format` VS Code task**, which chains `CSharpier Format` -> `.NET Build` -> `dotnet format style --verify-no-changes --severity=info`. The three task definitions in [`.vscode/tasks.json`][tasks] are the canonical command spec, and `Lint: All (CI parity)` runs the CI lint gate locally except shellcheck, shfmt, and the prose and repo gates.
- **This repo wires Husky.Net as its local commit gate.** `dotnet husky run` (configured in `.husky/task-runner.json`) runs CSharpier on the staged `.cs` files and the `dotnet format style` verify, and the hook also runs markdownlint and cspell through Docker when a Markdown file is staged, skipping quietly when Docker or the image is absent. CI enforces all of it regardless.
- **`dotnet format style --verify-no-changes --severity=info` gates the commit, and two IDE fixers bite.** CSharpier alone is not enough, since info-level IDE analyzers run in the `.NET Format` verify. `IDE0072` wants every enum member listed in a `switch` expression, and a `_ =>` discard arm does **not** satisfy it, so map values with explicit arms or a ternary chain rather than leaning on the fixer's `throw new NotImplementedException()`. `IDE0046` rejects `if (!cond) return false; return expr;`, so write the combined `return cond && expr;`. Run the `.NET Format` task before committing to surface these, and review any file it rewrote rather than staging it blind.
- **Repo-wide analyzer relaxations live in the root [`.editorconfig`][root] `[*.cs]` block, each with its reason.** They hold for every project here because PlexCleaner is a console application rather than a reusable library (public API surface rules, localization, `ConfigureAwait`, and a few false positives), and that is the only reason the root scope is justified. A new relaxation follows the scope order in [Analyzer Diagnostics and Suppressions](#analyzer-diagnostics-and-suppressions).
- **AOT is opt-in.** `<PublishAot>false</PublishAot>` is the default, matching the shipped builds, and the plugin loader compiles only in non-AOT builds. Publish with `-p:PublishAot=true` to build an AOT binary.
- **Internals are visible to the test project.** `PlexCleaner.csproj` declares `<InternalsVisibleTo Include="PlexCleanerTests" />`.

### Tests and Script Dependencies

- **A test lives in a `tests/` directory, never inside the production file it tests.** A deployed script may keep a `--selftest` that runs a small smoke check in seconds, and the case matrix lives in `tests/`. A self-test shipped inside the file it tests grows the file every reviewer reads, and its cases can come to outweigh the code they test.
- **A hub-hosted standalone script that needs a third-party library declares it in PEP 723 inline script metadata, and runs as `uv run --no-project --script "<path>"`.** The block opens on `# /// script`, closes on `# ///`, and carries `dependencies` and `requires-python`. The fleet already installs uv on hosts and in CI. `--no-project` keeps uv from syncing the project around a script that has no block yet, where it would write a lockfile and a virtual environment. A script with no such block runs under `python3` and uv alike. A hook an agent harness runs on every tool call stays standard-library only, since it runs before any toolchain is guaranteed.

### Interrupts in Python

- **SIGINT and SIGTERM take one path.** The entry point installs one handler with `signal.signal` for both signals. The handler records the first signal and raises `KeyboardInterrupt`, and returns at once on any later one. A later signal would cut the cleanup short, such as the SIGTERM that `uv run` forwards to a process group a Ctrl-C already reached. The handler takes SIGINT only where `signal.getsignal(signal.SIGINT)` is still `signal.default_int_handler`, so a SIGINT inherited as ignored stays ignored.
- **The entry point catches `KeyboardInterrupt` once, and any handler below it that catches the exception re-raises it.** It prints the line `CODESTYLE.md` "Interrupts" requires, then re-raises the signal the handler recorded. To re-raise, it flushes standard output and standard error inside `contextlib.suppress(OSError)`, restores the default handler with `signal.signal(signum, signal.SIG_DFL)`, then re-sends the signal with `os.kill(os.getpid(), signum)`. The suppression covers a pipe whose reader the same Ctrl-C ended. The default action ends the process without Python's own exit handling. So the flush comes first, and no cleanup on this path relies on an `atexit` handler or a finalizer. The re-raise runs outside every `with` block and `finally` clause, such as at the `__main__` call site, since none of them runs after it. A process the re-sent signal does not end, such as PID 1 in a container, then exits 128 plus the signal number. On Windows, `os.kill` ends the process with the signal number as its status, so there the entry point skips it and exits 130.
- **What the script holds is released by `with` blocks and `finally` clauses as the exception unwinds.** A `subprocess.Popen` child is stopped in a `finally` clause, since leaving its `with` block does not stop it. The clause calls `terminate()`, then `wait(timeout=...)`, such as 10 seconds. On `subprocess.TimeoutExpired`, it calls `kill()`, then `wait()`. The handler passes over a second Ctrl-C, so a child that ignores SIGTERM would otherwise hold the script. That child runs without `shell=True`, so `terminate()` reaches the command rather than a shell around it.
- **The rename over persistent state uses `os.replace`.** `os.rename` and `Path.rename` fail on Windows when the target exists.

### Interrupts in Shell

- **Cleanup of temporary paths and locks runs in the script's `EXIT` trap, set before the `INT` and `TERM` traps.** Bash runs that trap when SIGINT or SIGTERM ends the script, as well as on a normal exit. Set after the `TERM` trap, it does not run when that trap's re-sent SIGTERM ends the script.
- **Every script sets an `INT` trap and a `TERM` trap, which stop its children and re-raise the signal.** Each one sends SIGTERM with `kill` to the children the script started, then waits for them with `wait`. It then prints the line `CODESTYLE.md` "Interrupts" requires. Last, it clears its own trap with `trap - INT` or `trap - TERM` and re-sends the signal to the script with `kill -s INT "$$"` or `kill -s TERM "$$"`. It ends with `exit 130` or `exit 143`, which runs only where the re-sent signal does not end the script, such as PID 1 in a container. The children's process IDs are held in an array, such as `pids`, set to `()` before the traps are set. A trap skips the children's `kill` and the `wait` while `${#pids[@]}` is 0, a test `set -u` allows on an empty array in every Bash version. Under `set -u`, an unset one would end the trap before the line prints. The children's `kill` takes `2>/dev/null`, since a child that already exited makes it print an error. Both take `|| :`, since under `set -e` a non-zero status from either ends the trap before the line prints. SIGTERM is the signal sent because a background child ignores SIGINT. Other cleanup stays in the `EXIT` trap. A script that the `exec` case in `CODESTYLE.md` "Interrupts" frees from owing a trap sets neither trap.
- **A long-running external command runs in the background, and the script waits for it with `wait "$pid"`, so its exit status reaches `set -e`.** Bash runs a trap only after a foreground command returns, while a trapped signal ends a `wait` at once. Only the script's own shell starts such a child. One that a subshell or a pipeline element starts never reaches the script's array or its `wait`. A background child that reads standard input takes `<&0`, since bash otherwise gives it `/dev/null`. The trap's `kill` reaches only the process `$!` names. So a function, a group, a subshell, a pipeline, or `sh -c` runs in the foreground instead. There the trap runs once the command it interrupted returns, so nothing the script started is orphaned. A launcher, such as `uvx`, `uv run`, `uv pip install`, `dotnet`, or `xargs`, may run in the foreground too. One that does not stop the tool it starts on SIGTERM must run in the foreground. `uv pip install` is one when it builds an editable install or an sdist through a build backend that outlives uv on SIGTERM. A background child starts with SIGINT ignored, and the tool a launcher starts inherits that. So at Ctrl-C the tool runs on until the trap's SIGTERM reaches it through the launcher. In the foreground, Ctrl-C reaches the whole process group, the tool included. A SIGTERM sent to the script alone runs its `TERM` trap only once that foreground command returns. So a stop that must be prompt signals the process group. That group holds only the script and its command where the script leads it, as `setsid` starts one. The `exec` case in `CODESTYLE.md` "Interrupts" is the exception. The process a script `exec`s into replaces it, and a child handed across that `exec` is not waited for.
- **A deliberately POSIX `#!/bin/sh` script, such as a git hook, adapts the bullets above to what dash lacks.** Dash runs no `EXIT` trap when the re-sent signal ends the script. So the `INT` and `TERM` traps release the temporary paths and locks themselves, and the `EXIT` trap still covers an ordinary exit. A `/bin/sh` that is bash runs the `EXIT` trap after the signal trap too. So a release that cannot run twice, such as a lock's, sets its variable back to `""`. POSIX sh has no arrays, so the script runs one background child at a time. It holds that child's process ID in a scalar, such as `child`, set to `""` again after its `wait`. Every variable a trap reads, `child` and each temporary path included, is set to `""` before the traps are set. Under `set -u`, an unset one would end the trap before the signal is re-sent. A trap skips the child's `kill` and `wait` while `[ -n "$child" ]` fails, and skips the removal of a path still empty.

## PowerShell

*This section applies only to PowerShell scripts. A repo with no `.ps1` files still carries it (the file is carried whole) and ignores it.*

PowerShell is the native shell on Windows, so a Windows bootstrap and a Windows entry point over shared Python logic are written in it. Logic that needs its failure cases tested is Python on Windows too. PSScriptAnalyzer is the analyzer, and it runs every default rule through a `PSScriptAnalyzerSettings.psd1` at the repo root, which CI reads. A repo with `.ps1` files keeps its own copy. It excludes a rule below only where its own scripts meet that rule's reason, and states the reason there.

- **`PSAvoidUsingWriteHost`.** A script whose purpose is a console report writes it with `Write-Host`. Its functions return exit codes through the pipeline, so text sent with `Write-Output` would reach the caller as a return value.
- **`PSUseShouldProcessForStateChangingFunctions`.** A script that already carries its own preview and consent step, such as a dry-run switch and a confirm prompt, keeps them. Supporting `ShouldProcess` would add `-WhatIf` and `-Confirm` beside them, a second spelling of each.

The check is clean when `Invoke-ScriptAnalyzer -Path "<file>" -Settings ./PSScriptAnalyzerSettings.psd1` reports no finding for any tracked `.ps1` file, as CI requires. Run the check per `GOVERNANCE.md` "Running the Linters Locally (Known-Working Invocations)", not by probing `command -v pwsh`. That section is hub-only, read in a hub checkout rather than carried into every fleet repo. Windows batch (`.cmd` and `.bat`) appears only as a shim that puts a command on `PATH`, by decision, so it has no section here.
